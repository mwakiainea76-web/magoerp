

Software documentation is the collection of documents that explain:

* Why the system exists
* How it works
* How it is designed
* How to install it
* How to use it
* How to maintain it
* How to extend it
* How to troubleshoot it

Think of it as the "manual" for developers, administrators, testers, and future maintainers.

---

# Types of Documentation

## 1. Project Documentation

Explains the project itself.

Example

```
School ERP

Purpose

Goals

Technology stack

Architecture

Features

Roadmap
```

---

## 2. Architecture Documentation

This is the most important document.

It explains

* overall architecture
* backend
* frontend
* APIs
* database
* authentication
* caching
* queues
* security
* deployment

```

↓

## 3. Database Documentation

Every table should be documented.

Example

```

Also include

* ER diagrams
* relationship explanations
* indexing strategy
* migration history

## 4. API Documentation

Every endpoint should have

```

Method

Description

Authentication

Permissions

Request

Response

Validation

Errors

Examples
```

Example

```
POST /api/login
```

Should explain everything.

Instead of only generating code, it should also generate documentation.

Whenever it creates

* a migration
* a service
* an API
* middleware
* a React page
* a component
* a module

it should automatically update the relevant documentation.

Documentation should never become outdated.

---



This is the instruction i want you to  follow to create  a agreat documentation:

> You are the project's Software Architect and Technical Writer. Every feature you design or implement must also be documented. Documentation is a first-class deliverable, not an afterthought.
>
> Maintain a `/docs` directory at the root of the repository. Whenever you create, modify, or remove a feature, update the relevant documentation in the same task.
>
> Document the system at multiple levels: project overview, architecture, database schema, REST APIs, backend modules, frontend modules, security, deployment, testing, coding standards, and operations.
>
> Every REST endpoint must include its purpose, authentication requirements, permissions, request schema, response schema, validation rules, error responses, and usage examples.
>
> Every database table must include its purpose, relationships, indexes, constraints, and the modules that use it.
>
> Every module must document its responsibilities, workflows, services, events, middleware, dependencies, and extension points.
>
> Maintain Architecture Decision Records (ADRs) for significant technical decisions so future developers understand why important choices were made.
>
> Use Markdown for all documentation. Keep documentation synchronized with the codebase so it always reflects the current implementation.
>
> Documentation quality should be suitable for onboarding a senior developer with no prior knowledge of the project. It should be detailed, accurate, searchable, and easy to maintain.

For a project the size of your School ERP, this approach turns your documentation into a living knowledge base instead of a collection of notes that quickly become outdated.
